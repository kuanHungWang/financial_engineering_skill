Product guide

Describe the trade. Get a price.

The structured derivative pricer values exotic and structured products from a single YAML file that describes the trade. You write what the term sheet says; the engine checks it, picks a pricing method, and returns a fair value with the diagnostics you need to trust it.

Declarative

Products are assembled from tested blocks: observables, legs and masks. You never write a payoff formula.

Checked before it runs

Every error in the file is reported at once, with its exact path and a “did you mean” hint.

Right method, automatically

A QuantLib closed form when one matches the trade exactly; Monte Carlo otherwise, with a cross-check.

Reproducible

Same file and same seed give the same price, to the last digit.

Whole life of a trade

One spec prices at inception and on any later date. Past fixings come from a shared fixings file.

QuantLib conventions

Calendars, day counts, schedules and index definitions all come from QuantLib, not hand-rolled code.

What you can price

Barrier options, EKIAKO, autocallables, callable and puttable bonds, cancellable swaps, Bermudan options, equity-linked notes, fixed / floating / SOFR-compounded legs, inverse floaters, range accruals on equities, rates, CMS spreads or baskets, TARNs and kick-in coupons. See Coverage & limits for what is not supported yet.

Quick start

Five minutes from a clean checkout to a priced autocallable note.

  1. Set up once per machine. The script creates a virtual environment with QuantLib and prints the Python to use. 
    cd structured-derivative-pricer
PY=$(scripts/setup.sh)
  2. Validate the trade spec. It prints every error at once; exit code 0 means valid. 
    $PY scripts/price.py validate examples/autocallable_note.yaml
  3. Plan. See which method will be used and why, and what will be simulated. 
    $PY scripts/price.py plan examples/autocallable_note.yaml
  4. Price. Write the full result to a file as well as the terminal. 
    $PY scripts/price.py price examples/autocallable_note.yaml --out result.json
  5. Tighten the error without editing the file. 
    $PY scripts/price.py price examples/autocallable_note.yaml --set pricing.num_paths=100000

The trade you just priced

A 2-year autocallable note on SPX, from the investor’s side, notional 1,000,000: an 8% coupon paid quarterly, early redemption at par if SPX closes at or above 105% on a quarterly date, and a short down-and-in put (knock-in at 70%, observed at maturity) that exposes the investor to losses below the initial level.

valuation_date: 2026-09-28
market_data: market/mock_market.yaml

model: {type: black_scholes, underlying: SPX, discount_curve: USD}

schedules:
  quarterly: {type: generated, frequency: 3M, calendar: UnitedStates.NYSE, convention: ModifiedFollowing}
  autocall_dates: {type: generated, frequency: 3M, end: 2028-06-28, calendar: UnitedStates.NYSE,
                   convention: ModifiedFollowing}
  final: {type: dates, dates: [maturity]}

trade:
  id: ACN-SPX-2Y
  maturity: 2028-09-28
  legs:
    - {id: coupons, type: fixed_leg, rate: 0.08, notional: 1000000, schedule: quarterly,
       day_count: Thirty360.BondBasis}
    - {id: principal, type: fixed_amount, amount: 1000000, payment_date: maturity}
    - id: short_dip
      type: option_payoff
      underlying: SPX
      option_type: put
      strike: 1.0                      # 100% of the initial fixing
      notional: 1000000
      position: short                  # the investor sold this put
      conditions:
        - {type: knock_in, underlying: SPX, direction: down, barrier: 0.70, observation: final}
  termination_events:
    - {id: autocall, type: knock_out, underlying: SPX, direction: up, barrier: 1.05,
       observation: autocall_dates, rebate: 1000000, rebate_payment: at_hit, settle_on_event_date: true}

pricing: {num_paths: 20000, seed: 7}

The result, abridged (on mock market data):

  "method_reason": "no analytic pricer matches (european_vanilla: leg 'short_dip' has barrier conditions; ...)",

Read it as: fair value about 100.36% of notional (95% CI ±0.15%), a 72% chance of being autocalled and a 10.5% chance the put knocks in. Most of the value arrives through the autocall rebate, which is why the principal leg alone looks small.

How it works

The engine turns your spec into a graph of pre-tested components, then prices the graph.

curve→ discount→ underlying→ model→ scenario→ observables→ legs→ masks→ price

The scenario also produces discount factors, which go straight to pricing. The three highlighted stages are the building blocks you write in the spec.

Three stages, three commands

validate

Parses the document, checks every component against its schema, resolves every name (schedules, observables, curves, underlyings), checks model compatibility and lists missing past fixings.

plan

Validates, then chooses the method. Shows each closed form and why it does or does not match, the component graph, fixing-date counts and estimated memory.

price

Validates, plans, runs. Returns the price, its error, per-leg PVs, event probabilities, expected cashflows and model checks.

How the method is chosen

With pricing.method: auto (the default), a closed form is used only when it matches the trade exactly. Two exist today:

  • european_vanilla – one unconditioned option_payoff leg (plus fixed legs) and no termination events, priced with the model’s analytic European engine (Black-Scholes or Heston).
  • single_barrier – one option_payoff with one continuous knock-in / knock-out, priced with QuantLib’s analytic barrier engine (Black-Scholes only).

Everything else uses Monte Carlo. When Monte Carlo runs and a closed form also applies, both are priced and the gap is reported under cross_check. A trade that reads a past fixing is always priced by Monte Carlo, because closed forms start from today’s spot.

Command line

price.py catalog [KIND]                      # list component types and their fields (JSON)
price.py validate INPUT [--set k=v ...]      # check the input; print every error at once
price.py plan     INPUT [--set k=v ...]      # validate + pricing method + component graph
price.py price    INPUT [--set k=v ...] [--out result.json]
argumentmeaning
INPUTA YAML or JSON file, - for stdin, or a literal YAML/JSON string. Relative paths inside the document (market_data, fixings) resolve against the file’s folder.
KINDOne of curve, vol, swaption_vol, schedule, model, observable, leg, condition, event, analytic. Omit for all.
--set PATH=VALUEOverride a field without editing the file. Repeatable. PATH is dot-separated mapping keys (e.g. pricing.num_paths, valuation_date); VALUE is parsed as YAML. It cannot index into lists, so a single leg’s field cannot be overridden this way.
--out FILEprice only: also write the result JSON to FILE.

Useful recipes

# reprice the same trade on a later date (seasoned trade)
$PY scripts/price.py price trade.yaml --set valuation_date=2026-11-30 --set market_data=market_1130.yaml

# force Monte Carlo on a trade that has a closed form, to see the cross-check
$PY scripts/price.py price examples/vanilla_call.yaml --set pricing.method=mc

# just the fields of one component kind
$PY scripts/price.py catalog leg

# mock market data for a demo (labelled as mock)
$PY scripts/make_mock_market.py market.yaml --as-of 2026-09-28 --ticker SPX --spot 5000

Trade spec (YAML)

One document describes one trade: when to price it, against which market, under which model, and what it pays.

valuation_date: 2026-09-28          # pricing date (market data as_of should match)
market_data: market.yaml            # path relative to this file, or the market document inline
fixings: fixings.yaml               # optional past fixings shared by trades (path or inline)
model: {type: ..., ...}             # one model; it names the underlying(s) and discount curve
observables: {name: {type: ...}}    # named quantities read by legs, ranges, barriers
schedules: {name: {type: ...}}      # named date lists used by legs / conditions / events
trade:
  id: ...
  currency: USD
  effective_date: ...               # optional; default valuation_date (accrual start)
  maturity: 2027-09-28              # ISO date or tenor from effective_date ("1Y")
  calendar: WeekendsOnly            # adjusts dates given as tenors
  business_day_convention: ModifiedFollowing
  reference_levels: {SPX: 5012.3}   # optional initial fixings for relative strikes / barriers
  history: {SPX: {2026-07-28: 5012.3}}   # optional inline past closes; win over the fixings file
  legs: [...]
  termination_events: [...]
pricing: {method: auto, num_paths: 20000, seed: 42, antithetic: true}

Writing dates

Anywhere a date is expected you may write an ISO date (2027-09-28), a symbol (valuation_date, effective_date, maturity), or a tenor (6M, relative to effective_date or to a schedule’s start). Tenor dates are business-day adjusted with the trade’s calendar.

Values that change by period

Coupon notional, fixed rate, floating gearing / spread / cap / floor, and each range’s lower / upper accept three forms:

rate: 0.05                                   # the same in every period
upper: [0.045, 0.045, 0.05, 0.05]            # one per schedule period, paid periods included
upper: {effective_date: 0.045, 4Y: 0.05}     # steps keyed by period start
cap: {effective_date: null, 2Y: 0.06}        # null = no cap / floor / bound in those periods

A step-up coupon, a range that widens each year, a cap that starts in year 3 and amortising coupon notionals are all data, not new components.

Market data & fixings

Market data is a snapshot as of one date. Past fixings live in a separate file that only grows.

Fixings file

Shared by every trade and appended each day. A run ignores dates on or after its valuation date, so one file serves the whole life of a trade, and back-dated runs.

equities:                     # closing levels by model underlying name
  SPX: {2026-07-28: 4990.84, 2026-07-29: 4880.81, ...}
rates:                        # fixings by name; a rate observable reads its fixings_key (default: its name)
  USD-SOFR: {2026-09-24: 0.0431, 2026-09-25: 0.0430}
  • Equity history is closing levels, shared by every observable, barrier and range on that underlying.
  • An observable’s own history holds its own values (performances for a performance observable, rates for a rate) and overrides the shared levels date by date.
  • Composites (linear, min_of, max_of) read the history of their leaves.
  • Validation lists, per input path, every past date that has no fixing.

Building blocks

Every product is a combination of three kinds of block, read through one model.

Observables – what is watched

typevalue on fixing date ttypical use
equitylevel St, or performance St / SrefEvery model underlying is also usable by name as its level.
term_ratesimple forward over the index tenorEURIBOR 6M, 3M TAIFX, term SOFR
swap_ratepar swap rateCMS
overnight_rate1-business-day simple rateSOFR, ESTR, TONA; the index of compounded legs
linearconstant + Σ weight · observableSpreads [1, -1], baskets, inverse floater K − m·L

Name a QuantLib index with quantlib_index (Sofr, Euribor, EuriborSwapIsdaFixA, …) whenever QuantLib has it. Give the custom fields only for indices it lacks, such as TAIFX.

Legs – what is paid

typecashflow
fixed_legnotional · rate · τ per period
floating_legnotional · clip(gearing · X + spread, floor, cap) · τ. Fixed in advance, in arrears, or compounded in arrears with lockout.
range_accrualnotional · rate · τ · (days on which every range holds / observation days). Fixed or floating coupon.
option_payoffnotional · max(φ · (XT − K), 0) on an underlying (relative or absolute strike) or an observable
fixed_amounta known amount on one date (principal, fees)

A schedule lists accrual end dates; the first period starts at accrual_start (default effective_date). Payment is the end date plus payment_lag business days. Each leg has a position: long (the holder receives) or short (the holder pays).

Masks – when it is paid

maskwhereeffect
knock_in conditionon a legKick-in: a cashflow is paid only if the barrier was hit on or before its cut-off.
knock_out conditionon a legA cashflow is paid only if the barrier was not hit on or before its cut-off.
knock_out eventtradeTermination on the first hit (autocall); later cashflows cancelled, optional rebate.
target eventtradeTARN: terminates when accumulated coupons of the listed legs reach the target.
bermudan_call eventtradeOptional early termination by one party on a schedule: callable, puttable, cancellable, Bermudan option. Decided by Longstaff-Schwartz.

The cut-off of a cashflow is an option’s expiry, a coupon period’s accrual end, or a fixed amount’s payment date.

Bermudan exercise in brief

  • exerciser: issuer – the payer calls or cancels when that is cheaper than continuing (callable bond, cancellable note).
  • exerciser: holder – the holder puts when that is worth more (puttable bond, Bermudan option).
  • exercise_price is the cash the holder receives: 1000000 for a call at par on a 1,000,000 note, 0 for a free cancellation.
  • Leave out the date the principal leg pays (usually maturity). One bermudan_call per trade.
  • The fitted rule is slightly sub-optimal, so the price leans against the exerciser. Compare it with events.<id>.policy.in_sample_price: a gap of more than a few standard errors means the regressors miss the decision’s driver.

Models

typeunderlyingsratesclosed forms
black_scholesone, or several with explicit correlationdeterministicEuropean, single continuous barrier
hestonone; given or calibrated parametersdeterministicEuropean
hull_whitenone (rates only)stochastic 1-factor; given or calibrated to ATM swaptionsnone
  • A vol surface under black_scholes gives Dupire local vol, matching all vanilla prices.
  • Any optionality on a rate (cap, floor, inverse floater, rate range or barrier) needs hull_white; the validator rejects it under the equity models, whose rates are deterministic.
  • Hull-White is one-factor, so all rates move together. That understates the volatility of a CMS spread; say so when reporting one.

Conventions

Read these before writing a spec. Most pricing mistakes are one of them.

topicrule
PerspectivePriced from the holder’s view. position: long receives, short pays. An investor who sold a put inside a note is short that leg. A swap is one long and one short leg.
Relative vs absoluteOn an underlying, strikes and barriers are relative by default: 1.0 is 100% of the initial fixing. On an observable they are absolute in its units; for % of initial use an equity observable with mode: performance.
Option payoff unitsRelative strike: notional × max(φ·(ST/Sref − k), 0). Absolute strike: notional × max(φ·(XT − K), 0), where notional is the number of units.
Barrier touchup: breached when value ≥ B. down: breached when value ≤ B.
ObservationAt expiry only: a dates schedule [maturity]. Daily closes: a generated schedule with frequency: 1D and the right calendar. Quarterly: frequency: 3M. continuous is for closed forms only.
RebatesCash amounts, not percentages. An autocall’s par redemption is rebate: <notional>. Do not observe the autocall on the date the principal pays, or par is paid twice.
SchedulesExclude their start date unless include_start: true.
NumbersRates, vols and levels are decimals: 4.25% is 0.0425. A TARN target is cash: write 12% of 1,000,000 as 120000.

Two ambiguities matter most when reading a term sheet: whether a barrier is observed at expiry only or daily, and whether a level is a % of the initial fixing or an absolute price. Resolve both before writing anything. Then check plan: a daily barrier over 1Y shows about 250 fixing dates; if it shows 1, you observed it at expiry only.

When reporting a price, give the price with its confidence interval, the method, the key probabilities, every warning, and the model assumptions: model type, and whether the data is mock. For path-dependent products, pricing under both black_scholes (local vol) and heston shows model risk.

Fixing errors

validate reports every problem in one pass. Each error names the exact input path and, where it can, suggests the fix. Here is the autocallable note with three typos:

{
  "ok": false,
  "errors": [
    {"path": "trade.legs[2].conditions[0].observation",
     "message": "schedule 'finale' is not defined. Did you mean 'final'?",
     "hint": "defined schedules: ['autocall_dates', 'final', 'quarterly']; or use 'continuous' (analytic pricers only)"},
    {"path": "trade.legs[0].rate", "message": "Field required"},
    {"path": "trade.legs[0].rat",  "message": "unknown field (check spelling; see `price.py catalog`)"},
    {"path": "trade.legs[2].conditions[0].direction", "message": "Input should be 'up' or 'down'"}
  ],
  "warnings": []
}

Fix them all, then validate again. Common messages and what they mean:

messagewhat to do
“'SPX' needs N past closing level(s)”The trade reads dates before the valuation date. Add the closes to the fixings file; never invent them.
Optionality on a deterministic rateA cap, floor, range or barrier on a rate needs model: hull_white. Do not drop the feature to get past it.
Autocall observed on the principal datePar would be paid twice. End the autocall schedule before maturity.
Flat extrapolation usedA curve or surface does not reach the trade maturity. Get longer quotes, or report the warning.
num_paths must be evenAntithetic sampling pairs paths.

Coverage & limits

If a feature cannot be expressed with the catalog, the right answer is to say so, naming the missing component. Never approximate it away.

Not supported yet

  • More than one Bermudan exercise right per trade (e.g. both an issuer call and a holder put).
  • American (continuous) exercise. A daily bermudan_call schedule approximates it, if the user agrees.
  • Equity plus stochastic-rate hybrids.
  • FX, quanto and multi-currency trades.
  • Snowball / memory coupons.
  • Digital coupons other than range accrual.
  • Past monitoring of a continuous barrier: closed forms only look forward from today.
  • Custom payoff code (planned as an extension point).

Seasoned trades

Write the spec once, with an explicit effective_date. It then prices on any date of its life by changing only valuation_date and the market data, while the fixings file keeps growing. Every payoff reads past dates from history and later dates from the simulation; a fixing on the valuation date is simulated from today’s spot. A few things are not fixings and behave specifically:

featurebefore the valuation date
CashflowsPaid on or before the valuation date: dropped. The current period keeps its full accrual.
knock_out eventA past hit is an error: the trade has already terminated.
target (TARN)Paid coupons are recomputed from past fixings; give accumulated: <cash> if those are unavailable.
bermudan_callOnly exercise dates after the valuation date count.
observation: continuousMonitored forward from today only (warning): confirm the barrier was not hit.

Extending

For developers adding a component, not for pricing a trade.

  • Each component is a class registered with @register(kind, type) and a pydantic Spec in pricer/registry.py. A new observable, leg, condition, event, model or analytic pricer is one class.
  • Legs, conditions and events read the market only through observables (p.obs(name, dates)) and declare their dates through obs.requirements. That is what makes past fixings work for any payoff; a test enforces it.
  • Validation, the catalog, the plan graph and this page’s reference pick a new component up automatically.
  • Add a regression test in tests/ against a closed form or a limiting case, and run $PY -m pytest structured-derivative-pricer/tests -q.
